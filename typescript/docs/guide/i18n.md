# Internationalization (i18n)

Ox-Watt provides an internationalization module built on top of [Vue I18n](https://vue-i18n.intlify.dev/).

The module provides a consistent way to register, discover and load translation resources across applications and packages. It also defines conventions for translating application models and enums.

Ox-Watt does not attempt to replace Vue I18n. Instead, it provides an integration layer that handles locale resource management and exposes a simplified API.

## 1. Overview

The `i18n` module is responsible for:

- Detecting the preferred application locale.
- Registering translation resources from multiple packages.
- Loading locale resources on demand.
- Loading the fallback locale before the application starts.
- Exposing translation functions.
- Defining conventions for model and enum translations.

Vue I18n remains responsible for the actual translation engine, including message formatting, pluralization, interpolation and fallback resolution.

See the [Vue I18n documentation](https://vue-i18n.intlify.dev/guide/) for the complete reference.

## 2. Locale detection

Ox-Watt provides automatic locale detection through `detectLocale()`.

The locale is determined using the following priority:

1. Explicit locale provided during initialization.
2. Browser cookie.
3. HTML document language (`document.documentElement.lang`).
4. Browser language preference (`navigator.language`).
5. Configured fallback locale.

The default cookie name is `language`.

For example, an application can specify its preferred locale through a cookie:

```http
Set-Cookie: language=fr
```

Or through the HTML document:

```html
<html lang="fr">
```

### Locale format

Ox-Watt currently uses primary language codes rather than regional variants.

For example:

| Input | Normalized locale |
|---|---|
| `en` | `en` |
| `fr` | `fr` |
| `fr-BE` | `fr` |
| `en-US` | `en` |
| `nl-BE` | `nl` |

Regional variants are therefore normalized to their primary language.

Locale detection does not modify the cookie or the document language. Persistence and synchronization with the application environment remain the application's responsibility.

## 3. Locale resources

Translation resources can originate from multiple sources:

- Static resources bundled with JavaScript packages.
- Resources provided by application packages and their dependencies.
- Resources injected into the HTML document by the backend.

All resources are loaded lazily when their locale is requested.

### 3.1. Static package resources

Packages can expose their locale resources through `import.meta.glob()`.

A package should provide an `i18n` entry point exporting its locale loaders.

For example, in `@oxylus/core/i18n`:

```ts
/**
 * Locale resources provided by the core package.
 */
export const localeLoaders = [
    import.meta.glob('./locales/*.json', { import: 'default' }),
];
```

A package can also include resources from its dependencies:

```ts
import { localeLoaders as coreLocales } from '@oxylus/core/i18n';
import { localeLoaders as organizationLocales } from '@oxylus/organizations/i18n';

/**
 * Locale resources provided by the contacts package and its dependencies.
 */
export const localeLoaders = [
    ...coreLocales,
    ...organizationLocales,
    import.meta.glob('./locales/*.json', { import: 'default' }),
];
```

This allows applications to register the resources of their packages without having to manage the dependency graph themselves.

### 3.2. Locale filenames

Locale files are named using the locale they provide.

For example:

```text
locales/
├── en.json
└── fr.json
```

The locale is extracted from the filename.

Regional variants are not currently supported.

### 3.3. Resources provided by the backend

The backend can provide translation resources directly in the HTML document.

This is useful when translations are generated dynamically, for example from Django models or application-specific backend configuration.

Resources are declared using script elements with a `data-locale` attribute.

A resource can either reference an external JSON file:

```html
<script
    type="application/json"
    data-locale="fr"
    src="/locales/fr.json"
></script>
```

Or contain its JSON data inline:

```html
<script type="application/json" data-locale="fr">
{
    "application": {
        "title": "My application"
    }
}
</script>
```

All matching resources for a requested locale are loaded.

This allows multiple backend components to contribute translations independently.

### 3.4. Resource merging

Resources from different sources are merged into the Vue I18n message catalog.

Nested objects are supported.

When multiple resources define the same translation key, the value from the resource merged last takes precedence.

Applications should therefore avoid defining conflicting keys unless an override is intentional.

## 4. Using the library

### 4.1. Registering resources

Before initializing the application, register the locale loaders provided by its packages.

```ts
import { i18n } from '@oxylus/i18n';
import { localeLoaders as coreLocales } from '@oxylus/core/i18n';
import { localeLoaders as contactsLocales } from '@oxylus/contacts/i18n';

i18n.register([
    ...coreLocales,
    ...contactsLocales,
]);
```

Registration should happen before initialization.

### 4.2. Initializing i18n

Initialize the translation system before mounting the Vue application.

```ts
import { createApp } from 'vue';
import { i18n } from '@oxylus/i18n';
import App from './App.vue';

const app = createApp(App);

await i18n.initialize({
    fallbackLocale: 'en',
});

app.use(i18n.plugin);

app.mount('#app');
```

Initialization detects the preferred locale, then loads both the fallback locale and the selected locale before activating the translation system.

This ensures that translations are available when the application first renders, avoiding an untranslated initial state.

### 4.3. Translating messages

The module exposes translation functions directly.

```ts
import { t, te } from '@oxylus/i18n';

const title = t('application.title');

const exists = te('application.description');
```

`t()` delegates translation to Vue I18n.

It supports Vue I18n's translation arguments, including pluralization and interpolation.

For example:

```ts
t('messages.welcome', { name: 'John' });

t('messages.items', 2);
```

`te()` checks whether a translation key exists.

For the complete set of supported arguments and message syntax, refer to the [Vue I18n translation API](https://vue-i18n.intlify.dev/api/composition.html#t).

### 4.4. Changing the locale

The active locale can be changed at runtime:

```ts
await i18n.setLocale('fr');
```

The requested locale and the fallback locale are loaded before the active locale changes.

`setLocale()` does not persist the selected locale in a cookie or modify the HTML document language.

The application is responsible for synchronizing those values when necessary.

### 4.5. Accessing Vue I18n

The module exposes the underlying Vue I18n integration through:

- `i18n.plugin`: Vue plugin to install on the application.
- `i18n.composer`: Vue I18n composer.
- `i18n.locale`: currently active locale.

The composer provides access to Vue I18n functionality that is not explicitly exposed by Ox-Watt.

Refer to the [Vue I18n API reference](https://vue-i18n.intlify.dev/api/composition.html) for additional functionality.

## 5. Translation conventions

Ox-Watt defines standard namespaces for application translations.

These conventions allow packages to contribute translations independently while avoiding collisions between applications.

### 5.1. General application translations

Application-specific translations should be grouped under a namespace identifying their purpose.

For example:

```json
{
    "application": {
        "title": "My application"
    },
    "messages": {
        "welcome": "Welcome, {name}!"
    }
}
```

Use descriptive namespaces and avoid generic keys at the root level.

### 5.2. Model translations

Model translations use the following namespace:

```text
models.<app_label>.<model_name>
```

The application label and model name should use their Django identifiers, normalized to lowercase.

For example, a `Contact` model in the `contacts` application uses:

```text
models.contacts.contact
```

Model translations should be structured as follows:

```json
{
    "models": {
        "contacts": {
            "contact": {
                "label": "Contact | Contacts",
                "fields": {
                    "first_name": "First name",
                    "last_name": "Last name",
                    "email": "Email address"
                }
            }
        }
    }
}
```

The `label` message uses Vue I18n pluralization syntax. The model's singular and plural labels are therefore handled by the same translation key.

Field translations are grouped under `fields`, using the actual model field names.

This convention allows model metadata to resolve translation keys consistently without storing translated labels in the model definitions.

### 5.3. Enum translations

Enum translations use the following namespace:

```text
enums.<app_label>.<enum_name>
```

Enum names should use their stable application-level identifiers, normalized to lowercase.

For example:

```json
{
    "enums": {
        "contacts": {
            "contact_status": {
                "active": "Active",
                "inactive": "Inactive",
                "archived": "Archived"
            }
        }
    }
}
```

Enum values should use their actual serialized values as translation keys.

This ensures that translations remain independent from the display labels and can be resolved consistently across the frontend and backend.

### 5.4. Naming rules

The following rules apply to model and enum namespaces:

| Element | Convention | Example |
|---|---|---|
| Namespace | Lowercase | `models` |
| Django application | Application label | `contacts` |
| Model | Lowercase model name | `contact` |
| Model field | Actual field name | `first_name` |
| Enum | Stable enum identifier | `contact_status` |
| Enum value | Serialized value | `active` |

These identifiers should remain stable across locales and should not contain translated text.

## 6. Integration with application models

ADM models can use the standardized translation namespaces to expose their labels.

A model can provide:

- A translated singular label.
- A translated plural label.
- Translated field labels.

For example, the following calls illustrate the expected behavior:

```ts
// Model label
Contact.label();
Contact.labelPlural();

// A model's field label
Contact.label("first_name")
Contact.labelPlural("first_name")

// For any other translation you can use `i18n` static method:
Contact.i18n("description")
```

The model's translation key resolution is based on its application and model identity, not on its API endpoint or URL.

The actual translation is performed through the functions exported by `@oxylus/i18n`.

This keeps model metadata independent from the translation engine while ensuring that all models follow the same naming conventions.
